### F-01 — MAJOR / provenance and exported ancestry: a second-generation JSON audit loses the root driven-model record

**Source:** [`driven_reassembly.py` lines 96–127](https://github.com/physicsvigilante/conductor_sim/blob/e0ea76e80aca4b05cea7f16a12549c13670108d2/src/conductor_sim/driven_reassembly.py#L96-L127), especially lines 103–108. Compare [`structural_scenarios.py` lines 181–193](https://github.com/physicsvigilante/conductor_sim/blob/e0ea76e80aca4b05cea7f16a12549c13670108d2/src/conductor_sim/structural_scenarios.py#L181-L193). Relevant promises: [frozen charter lines 21–29, 75–81](https://github.com/physicsvigilante/conductor_sim/blob/e0ea76e80aca4b05cea7f16a12549c13670108d2/docs/m26a_charter.md#L21-L29) and the [M26a description lines 67–74](https://github.com/physicsvigilante/conductor_sim/blob/e0ea76e80aca4b05cea7f16a12549c13670108d2/docs/m26a.md#L67-L74).

**Reproduction performed with the pinned source (Python 3.13):** Author a root `DrivenModel` with model ID `review:ROOTMODEL` and provenance `ROOT_DRIVEN_PROVENANCE_26A`. Reassemble it once to add held source `point:temporary` (`review:GEN1MODEL`), then reassemble that `DrivenReassembly` to remove the source (`review:GEN2MODEL`), retaining both live parents. Serialize only `second.as_dict()`.

**Expected under the packet's complete driven-model-ancestry claim:** The detached final audit either carries retrievable original driven-model details, or clearly specifies that it is merely one link in an externally retained hash chain. M22a base ancestry already embeds `parent_assembly` recursively.

**Observed:** `second.parent.parent is root` is true: **live Python ancestry is correct**. The exported M22a `base_assembly.parent_assembly` exists and retains the root base scenario and provenance. But `second.as_dict()` includes only the immediate `parent_model` and `parent_driven_assembly_revision_id`; it has no prior driven-assembly payload, no `review:ROOTMODEL`, and no `ROOT_DRIVEN_PROVENANCE_26A`. The hash correctly equals `first.revision_id`, but the final exported record alone cannot reconstruct or audit the original driven parent. This is not evidence of a forged hash or wrong physical ancestry at runtime.

**Smallest correction:** Decide and make explicit whether `DrivenReassembly.as_dict()` promises a self-contained driven-ancestry export. If yes, include previous driven assembly records (possibly a bounded, nonduplicating ancestry list) and add a two-plus-generation regression asserting root model ID/provenance, immediate-parent linkage, changes and hashes are recoverable. If intentionally hash-linked rather than self-contained, correct the broad *complete driven ancestry* claim in technical/review documentation, require retention of all separately exported parent records, and add a reference-chain integrity regression. Keep the frozen charter unchanged; document any amendment separately. This is an audit/evidence issue, **not** a reason to change the laws or integrator.

**Evidence type / confidence:** Executed novel two-generation case and inspected actual JSON; high confidence on missing fields. The required export completeness is a contract interpretation that must be settled by the owner/implementer.

### F-02 — MINOR / identity-namespace contract ambiguity (not a demonstrated numerical failure)

**Source:** [`driven_reassembly.py` lines 30–45, 130–156](https://github.com/physicsvigilante/conductor_sim/blob/e0ea76e80aca4b05cea7f16a12549c13670108d2/src/conductor_sim/driven_reassembly.py#L130-L156), [`driven_motion.py` lines 94–103](https://github.com/physicsvigilante/conductor_sim/blob/e0ea76e80aca4b05cea7f16a12549c13670108d2/src/conductor_sim/driven_motion.py#L94-L103), [`structural_scenarios.py` lines 23–40, 209–240](https://github.com/physicsvigilante/conductor_sim/blob/e0ea76e80aca4b05cea7f16a12549c13670108d2/src/conductor_sim/structural_scenarios.py#L209-L240), and [charter N3 lines 63–64](https://github.com/physicsvigilante/conductor_sim/blob/e0ea76e80aca4b05cea7f16a12549c13670108d2/docs/m26a_charter.md#L63-L64).

**Reproduced:** A new `NamedSource` with source ID identical to `parent.model_id` (`re:parent`) was **accepted**, as was a source ID identical to the newly authored `model_id` (`re:newsame`). By contrast, source IDs `field:scheduled` and `drag:medium` were correctly **refused**. Existing model-ID reuse along driven ancestry and retired source-ID reuse were refused.

**Interpretation:** Code currently treats **model IDs** and **physical-component IDs** as separate namespaces. This can be valid; it does not corrupt the force calculation. However the charter says a source ID colliding with other retained identities is refused and does not explicitly define the exception. **Clarify** whether cross-kind model/source collisions are intentionally permitted. If namespace separation is intended, state it and test it; if globally unique retained IDs are required, reject collisions with current/ancestral driven model IDs (and define whether scenario IDs also count). Do not call this an engine defect until the namespace rule is fixed.

**Evidence type / confidence:** Executed novel positive collision and negative role-collision inputs; high confidence on behavior, medium on whether it violates the intended policy.
