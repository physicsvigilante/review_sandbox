## Findings

### F-01 — MAJOR / source-fidelity: edge-on ring's open-end circles are inside the actual rim endpoints

**Source:** [`src/conductor_sim/source_geometry.py` lines 218–230](https://github.com/physicsvigilante/conductor_sim/blob/31ee492bd6070e8b74bf233c44a86de6301af827/src/conductor_sim/source_geometry.py#L218-L230), especially line 229. The Python rim basis and the 81-point rim path are correct; the **additional endpoint-circle placement** is not generally correct.

**Independent input / admissibility:** Reuse the existing public two-coaxial-ring model (world-x axis, ring radius `R=0.3 m`, centres `(0,0,0)` and `(0.4,0,0)`, moving charge initially at `(0.18,0,0)`, initial velocity, gravity and scheduled fields all along x), but choose the qualified physical viewing-plane normal `n=(0,1/sqrt(2),1/sqrt(2))` instead of `(0,1,0)`. The x-axis remains within the plane, the source fields remain axis-only and the same x-axis trajectory is physically admissible under the pinned qualifier. The rim basis for each x-axis ring is world y/z and projects to `a=(0,-R/sqrt(2))`, `b=(0,+R/sqrt(2))`.

**Expected:** The edge-on projected *rim* and its specially drawn open-end circles have extrema at ±`R=0.3 m` from the centre, since the projected curve is `a cos(t)+b sin(t)` and its major semiaxis is `R`.

**Observed:** The renderer chooses `z = (|a| > |b| ? a : b)` and places its circles at ±`|z|=R/sqrt(2)=0.2121320344 m`. The drawn rim still extends to ±0.3 m, but the circles falsely mark interior locations. A **fresh Chromium replay** of the saved viewer with only its plane/derived geometry adjusted to this admissible rotation recorded four radius-4-pixel marker arcs displaced by **32.3825 screen pixels** from the true projected ends; the page had no JavaScript errors. The browser replay is **not** a fresh native-model execution and does not authenticate a newly revised scenario digest; the error itself follows directly from the exact pinned renderer and projection algebra.

**Correction:** Calculate actual major-axis endpoints of the projected ellipse/line from the two rim vectors (for example, principal eigenvector of `a a^T + b b^T`, and associated maximal semiaxis), rather than picking one projected rim-basis column. Preserve the already correct 81-point curve. Add a *qualifier-admitted* x-axis ring with 45° tilted motion-plane normal, both canvas and numeric endpoint assertions, and check both event and driven viewers. Do not modify any E/V law. **This finding blocks a source-geometry fidelity pass.**

### F-02 — MINOR / boundary semantics: a near-outside radial body can be labelled as intersecting

**Source:** [`source_geometry.py` lines 42–45 and 114–127](https://github.com/physicsvigilante/conductor_sim/blob/31ee492bd6070e8b74bf233c44a86de6301af827/src/conductor_sim/source_geometry.py#L114-L127). The rule declares omission only for `|h| > R + clearance`. For `R < |h| <= R+clearance`, it declares `slice-intersection` and clamps the negative radicand to zero radius, although the sphere/shell does not intersect the plane. Exact tangency is also not distinguished from a nonzero-area slice.

**Fresh independent arithmetic / possible qualified boundary:** `length_scale_m=1`, radial radius `R=5e-12 m` and signed centre offset `h=8e-12 m` give `clearance>=1e-11 m`, so the ledger says `slice-intersection` with `slice_radius_m=0`, although `|h|>R`. A source centre such as `(0.2,8e-12,0)`, particle at origin, motion plane normal world y, ordinary tiny nonzero charge and in-plane launch is inside the pinned `_in_plane` *numerical qualification tolerance* of `1e-11 * max(length_scale, distance)`; the field need not be ignored. This is a **source-derived boundary counterexample**, **not** an independently executed fresh `TestChargeMotionSpec`/viewer run.

**Correction / regression:** Keep numerical closeness and physical intersection distinct. Treat strictly outside `|h|>R` as no physical slice, and report near-contact uncertainty/roundoff separately where needed; explicitly identify exact tangency if displayed. Test `|h|<R`, `|h|=R`, and `|h|>R` at scale-separated radii. This is a narrow display-truth issue, not proof of solver error.

### F-03 — MINOR / qualification and identity-binding contract: the public helper alone does not authenticate a source-ID permutation

**Source:** [`source_geometry.py` lines 54–84](https://github.com/physicsvigilante/conductor_sim/blob/31ee492bd6070e8b74bf233c44a86de6301af827/src/conductor_sim/source_geometry.py#L54-L84) and [`scenarios.py`](https://github.com/physicsvigilante/conductor_sim/blob/31ee492bd6070e8b74bf233c44a86de6301af827/src/conductor_sim/scenarios.py). The helper checks annotation count, syntax and uniqueness but cannot compare arbitrary valid annotations to an independent trusted identity mapping. As a source-level counterexample, feeding an unchanged two-ring `spec` with unique annotations `(('ring:B','Ring B'),('ring:A','Ring A'))` associates the wrong IDs with the two source objects without violating these guards. This input has **not** been executed against a locally installed production package.

**Interpretation:** Normal event/driven renderers pass `spec` and `source_annotations` from the *same validated, immutable* `PrescribedScenario`; this avoids a routine mismatch, and the authored scenario revision digest already carries the identity assertion. Arbitrarily edited offline HTML is **not** a trusted import format and should not be treated as one. But the charter's broad B2 wording, “forged ID sequences,” is stronger than what the standalone `source_geometry(spec, annotations)` helper itself checks.

**Correction / regression:** Specify the actual trust boundary explicitly (trusted `PrescribedScenario`/`DrivenModel` rather than arbitrary independent arrays), or accept a trusted binding object into the helper and verify IDs against it. Add a case distinguishing a genuinely authored new identity from an unauthorized re-labelling. Do **not** introduce a universal scene graph or cryptographic HTML authentication merely to address this bounded display contract.
