## Findings

### F-01 — BLOCKER: stale graph after valid scenario replacement and later refusal; out-of-order scenario-import race

**Files:** [`viewer/source_preview/app.mjs` lines 81–107](https://github.com/physicsvigilante/sim_heat/blob/85ac4ce2ec7c8c7be5ab85bacf5a1b5ed7b76114/viewer/source_preview/app.mjs#L81-L107), especially `setScenario`, `compareError` and `variant-import`.

**Independent DOM reproduction:** start with truly H1-admitted D2 baseline and D2_K2 variant. Click **Inspect scenario graph** (graph displays `H1_D2_K2`). Import another genuinely admitted source-only JSON for D1 as the scenario. The comparison identity updates to `H1_D1`, but the graph, selected details and request area **continue displaying D2_K2**. Import malformed `{}` as a subsequent scenario: the comparison refuses and disables its scenario button, yet the old `H1_D2_K2` graph remains visible rather than reverting to baseline `H1_D2`. This was observed in Chromium DOM, not merely inferred.

**Cause:** `setScenario` changes `scenario` and calls `showComparison()` without re-rendering when the prior scenario is on screen. When the next import fails, `compareError` tests `preview === scenario` against the **new** scenario object, so it misses the still-rendered **previous** scenario and leaves its obsolete graph/details visible. Separately, I delayed the first of two overlapping scenario file reads in the DOM harness: a later fast S1 import rendered in the comparison, then the earlier slow D1 import overwrote it. `loadVersion` protects baseline replacements but does **not** advance on each scenario import.

**Impact:** teacher-facing source facts and requested observations may be attributed to the wrong or refused comparison; a refusal does not reliably clear obsolete evidence. **Required:** explicitly synchronize visible graph with successful scenario replacement or revert to baseline before showing the new comparison; clear the previous scenario on every refusal; introduce per-scenario generation tokens so only the most recent scenario selection can commit. Add real Chromium regressions for A-viewed → B-valid → C-invalid and slow-A/fast-B concurrent imports, asserting graph, details, requests, identity, buttons and comparison state consistently refer to one admitted display or a clear refusal.

### F-02 — BLOCKER: same study SHA with different model SHA passes as zero-difference comparison

**Files:** [`viewer/source_preview/compare_core.mjs` lines 18–46](https://github.com/physicsvigilante/sim_heat/blob/85ac4ce2ec7c8c7be5ab85bacf5a1b5ed7b76114/viewer/source_preview/compare_core.mjs#L18-L46); [`h1/study.py` lines 140–159](https://github.com/physicsvigilante/sim_heat/blob/85ac4ce2ec7c8c7be5ab85bacf5a1b5ed7b76114/h1/study.py#L140-L159).

**Independent exact-JS reproduction:** import the shipped `TEACH_SPLIT3.json` twice; on the variant modify only `variant.source.modelSha256 = 'a'.repeat(64)` and leave `studySha256` and all displayed model/study facts unchanged. `compareSourcePreviews(base, variant)` **accepts** and returns **zero changes**, despite displaying distinct model SHA-256 values for the same claimed study SHA-256.

**Cause:** the `studyShape()` projection compares `modelShape` but omits the model SHA field. Actual H1 `study.json` contains `model.sha256`; one byte-identical study SHA cannot legitimately refer to two different model hashes. This is an internally contradictory **display identity** even though browser imports are intentionally not source-authenticated. The existing tests catch same model hash/different model values and same study hash/different requests, but miss this cross-hash contradiction.

**Required:** bind `source.modelSha256` into the study-identity consistency check or reject same-study-hash/different-model-hash explicitly. Add a negative test even when all values, physical-port groups and provenance are otherwise identical; preserve legitimate cases with a common model hash but distinct study hashes.

### F-03 — MAJOR: source input and provenance changes are hidden when component kind changes

**File:** [`viewer/source_preview/compare_core.mjs` lines 55–78](https://github.com/physicsvigilante/sim_heat/blob/85ac4ce2ec7c8c7be5ab85bacf5a1b5ed7b76114/viewer/source_preview/compare_core.mjs#L55-L78).

**Independent exact-JS reproduction:** on a shape-valid imported scenario, change component `shortcut` from `RodArea` to `RodCircular`, replace its original `A` input with SI diameter `d`, and revise that input's attribution; give the variant distinct model/study SHAs. The comparison reports only `shortcut · kind` and **omits** all of the input and attribution differences. The same omission applies to added/removed components, where only kind/presence is listed.

**Cause:** both the missing-component and kind-change branches `continue` before input/provenance comparison. Browser imports are expressly shape-checked rather than authenticated, so this is a valid challenge of the claimed comparison UI; a genuinely authored separate H1 composition can also change component type (even though the special D2_K2 conductivity-revision grammar does not).

**Required:** show added/removed source-input and attribution inventories and distinguish changed types without hiding their authored fields/assumptions. Add cross-kind and add/remove component comparison regressions. This does **not** require a new physical law, numeric solve or apparatus branch.
