## F-01 — BLOCKER remains: selecting a scenario while baseline is pending is neither settled nor last-selection-wins

**Code:** [app.mjs lines 104–126](https://github.com/physicsvigilante/sim_heat/blob/9199e695f5aae410cb8d0e89f463b3b1b6e57c15/viewer/source_preview/app.mjs#L104-L126), [lines 128–162](https://github.com/physicsvigilante/sim_heat/blob/9199e695f5aae410cb8d0e89f463b3b1b6e57c15/viewer/source_preview/app.mjs#L128-L162).

**Passing correction boundary:** On a *loaded* baseline, scenarioVersion increments on every scenario-file selection, loadVersion rejects old-baseline work, the viewed A→accepted B graph/identity/details/requests change together, a refused C clears comparison and returns to baseline, and late slow A cannot overwrite fast B. The delayed startup VARIANT response is correctly ignored when the user imports B **after the startup baseline has loaded**. This reproduces the intended previously failing behavior.

**New independent reproduction A — stale checking state after baseline-file replacement:**

1. Begin on an admitted TEACH_SPLIT3 baseline. Select a different, valid baseline file whose File.text() remains pending; this clears baseline and starts a new loadVersion.
2. While that baseline read is pending, select a valid source-only scenario B whose File.text() resolves immediately.
3. B's scenario handler reaches the [conditional commit](https://github.com/physicsvigilante/sim_heat/blob/9199e695f5aae410cb8d0e89f463b3b1b6e57c15/viewer/source_preview/app.mjs#L117-L125) with current generation numbers **but baseline=null**, so it silently drops B. No comparison refusal or completed-state update occurs.
4. Resolve the new baseline file; the new graph and SHA display correctly, but the comparison status remains **“Checking newly selected source-only scenario…”** indefinitely, no scenario is admitted, and its view button stays disabled. All pending file reads have finished.

**New independent reproduction B — initial startup default overrides the user's scenario choice:**

1. Hold the initial default TEACH_SPLIT3 baseline fetch unresolved. Select a valid scenario-file B (study/model identity changed consistently) while that initial fetch is still pending. B's File.text() resolves first, but B is discarded because baseline is still null.
2. Release the initial baseline fetch. At [line 150](https://github.com/physicsvigilante/sim_heat/blob/9199e695f5aae410cb8d0e89f463b3b1b6e57c15/viewer/source_preview/app.mjs#L146-L155), initialScenarioGeneration is **reset to scenarioVersion after the user selection**, so the earlier user action is not treated as superseding the default scenario.
3. Deliver the default VARIANT A. The UI accepts and displays **DefaultScenario A** as the comparison, despite B having been the later user-chosen scenario. The scenario button is enabled for A; the user's B does not appear, and no refusal is shown.

Both repros used the **unmodified exact pinned app code**, synthetic valid source-only TEACH_SPLIT3-shaped payloads and controlled promises, not an alternative hand-written implementation of its state machine. They are source/UI sequencing findings, not evidence that native physics or genuine H1 source identity failed. The fact that browser files are display-schema checked rather than authenticated does not excuse silently replacing the user's chosen display.

**Root cause:** The handler only calls setScenario if baseline already exists when the scenario read resolves, but it does not queue or explicitly refuse a scenario selected during baseline admission. The baseline-import success path does not settle the stranded comparison status. On initial startup, resetting initialScenarioGeneration *after* the baseline fetch loses knowledge of scenario selections made while that fetch was pending, allowing a default to win.

**Required before F-01 closure:** Make pending-baseline behavior explicit and deterministic. Either (a) disable/refuse the scenario picker during each baseline load and give a final, visible refusal/ready state, or (b) queue the most recent selected scenario against the new baseline generation and evaluate it only once that baseline is admitted. Preserve an initial-startup user-selection generation barrier **from before** the first baseline fetch so a later default cannot override a user choice. Refused or superseded selections must never leave “Checking…” after all work settles. Add *real hosted Chromium* regressions delaying a baseline File.text() and the initial baseline fetch, with user scenario selection in each pending interval; assert correct final graph, identity, requests, diff, error/status and button state, including no default overwrite. Retain existing A→B→C, slow→fast, CSP and Host/route refusals. A new code SHA and exact-head green PUSH/PR CI should precede the next targeted review.
