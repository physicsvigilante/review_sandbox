## F-01 — MAJOR, scoped design correction: define the independent oracle's arithmetic target before applying 100× to constants

**Sources:** `qualification/h1_n1/REFERENCE-CONTRACT.md`, “Proposed rigorous enclosure algorithm” steps 1–5; `qualification/h1_n1/PLAN.md` section 3; `h1/reference.py` lines 113–121 and 298–334; `experiments/h1_spike/SimHeat.mo` circular-area definition. The new contract instructs the checker to start from *exact source-decimal rational numbers*, separately document binary64 input/operation conversion, and certify every float64 reference against an independently enclosed answer with discrepancy at most `epsilon_q/100`. The unchanged checking implementation assigns **static parameter** exports C/G/A an allowance of `64 * ulp(reference_scale)`, rather than the ordinary K/W/J physical-output formula.

**Independently reproducible counterexample (no compiler, native data or reference regeneration):** For original `T10.G`, the public/source inputs are `k=95`, `A=0.00013` m², `L=0.40` m. Their exact rational physical result is

`G_exact = 95 * (13/100000) / (2/5) = 247/8000 = 0.030875 W/K`.

The existing float64 checking expression `95 * 0.00013 / 0.40` evaluates to `0.030874999999999993` W/K. Its ULP is `3.469446951953614e-18` W/K; the unchanged static allowance is `64 ULP = 2.220446049250313e-16` W/K, and **1/100 of that is `2.220446049250313e-18` W/K**. The absolute float64-to-exact-decimal discrepancy is `7.271960811294776e-18` W/K, **3.275× the proposed reference-error budget**. Even treating the *parsed binary64 input literals* as exact rational numbers but not reproducing intermediate rounding yields `2.8532948573301024e-18` W/K, **1.285× the 1/100 budget**. These are rational/binary arithmetic checks of a declared source formula, not a failed native comparison or an interval-certificate implementation.

A second **arithmetic-order warning**, not evidence of actual OMC output: for `T06.A`, `math.pi * (0.016/2)**2` (the float64 reference expression) and `math.pi * 0.016 * 0.016 / 4` (the source Modelica expression's apparent order) differ by **one binary64 ULP** in ordinary Python evaluation. This exceeds the nominal **0.64 ULP** reference-certification budget. Compiler constant-folding, the actual Modelica Pi value and effective evaluation order have **not** been observed here. Neither this warning nor T10 proves the native constant is outside the **full 64-ULP comparison allowance**.

**Why this matters:** The proposed interval Taylor/squaring algorithm may rigorously enclose the *mathematical* temperatures and flows, but a correct enclosure of exact-decimal static conductance can still be too distant from the unchanged float64 reference to satisfy the much tighter `epsilon/100` test. Conversely, constructing an oracle around a selected Python/Modelica double-rounding order only after inspecting the checking or native result risks circular certification. This ambiguity belongs in the **pre-native design**, not merely in an unreviewed future implementation. The contract already commendably says to *refuse* rather than waive accuracy; that prevents false success, but does not yet define a fully reviewable, feasible constant-certificate target.

**Smallest correction:** Prospectively pin a **two-level, per-export arithmetic interpretation ledger**: (1) the physical mathematical result implied by the original exact source decimals/geometry and a rigorous enclosure; (2) the **declared, independently justified float64 parameter-export target** (including source-literal conversion, Pi, constant-folding/evaluation order and intermediate rounding), with its own deterministic proof of relation to (1) and to the unchanged checking value. Spell out which enclosure is compared to `v_ref` for the **mandatory 100×** certificate and how the unchanged **64-ULP native comparison policy** is preserved; do **not** fit a target after inspecting outputs, silently exempt constants, relax 100×, alter original `model.mo`, or replace historical references. Provide one predeclared worked/refusal test each for `T10.G` and `T06.A/G`, including binary64 intermediate-rounding variations, and a negative case that fails when `delta > epsilon/100`. If a coherent interpretation still cannot achieve 100×, stop at the documented reference gate. This is a **focused contract change**; no new physical law, production solver or broader redesign is required.
