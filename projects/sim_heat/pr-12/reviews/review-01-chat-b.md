## Findings

### F-01 — **major, release-blocking for an evidence-critical integration** — MAT channel uniqueness mislabeled as independent measurement

- **Source:** [`h1/matv4.py` lines 171–198](https://github.com/physicsvigilante/sim_heat/blob/f2bb5369425a250cef78b74baaf486925f8fa6bd/h1/matv4.py#L171-L198), especially `'channelIsIndependentMeasurement': len(channels[(channel, abs(signed))]) == 1`. `h1/tests/test_matv4.py` covers shared/negated aliases but not this semantic mismatch for individually indexed parameter rows.
- **Reproducible input:** Actual archived [bridge artifact 14155084346](https://github.com/physicsvigilante/sim_heat/actions/runs/43699424883/artifacts/14155084346), `case_01/model_res.mat` (SHA-256 `e1da06d7223dd271317881b2d737b73c40ec643a8d533568bf7ef3bfbb5443a9`), and its `case_01/mat_provenance.json`. Independently read `name`, `dataInfo`, `data_1` and `data_2` from raw MAT; compare with the sidecar.
- **Expected:** A unique MAT data row proves only that the export is **not sharing its indexed channel** with another named export. A `data_1` source is a stored parameter, **not an independently measured physical quantity**; even a unique `data_2` row is a solver-exported value, not external measurement authentication. The status field must not say otherwise.
- **Observed:** Nine exports, including `bridge.G`, `left.C`, `right.C`, `heated.T` and `cooled.T`, simultaneously have `origin: "mat_parameter"`, `matTable: "data_1"` and `channelIsIndependentMeasurement: true`. Example: `bridge.G` comes from `data_1`, row 3, shared names `["bridge.G"]`, but is labeled an independent measurement. This follows directly from the source boolean formula and was observed in real saved native evidence, not just a hypothetical fixture.
- **Impact:** Misleading audit metadata can cause downstream consumers/readers to overstate evidence independence, precisely the provenance boundary this R2 release is meant to preserve. **No false numerical PASS, invented parameter value or native-qualification status was demonstrated**: the actual checker separately says `nativeQualified=false`, and the numeric channel mapping matches recorded MAT values.
- **Correction:** Replace the ambiguous flag with e.g. `hasUniqueMATChannel` / `isUnaliasedMATChannel`, with clear documentation that it confers **no measurement independence**, or make the existing field conservatively false and separately report channel uniqueness. Add a regression with (a) unique `data_1` parameter, (b) direct unique `data_2` solver history and (c) signed/shared `data_2` aliases. Preserve already-published native sidecars as historical artifacts; explain the successor schema/meaning rather than rewriting them.
- **Evidence / confidence:** **Direct independent reproduction; high confidence.** This is a narrowly scoped provenance-language defect, not a new physics defect. Correct it in a new source SHA, rerun offline CI, and request targeted review of the changed semantics.

### F-02 — **minor, execution/trust-boundary clarification** — “offline CI” is not an air-gapped or no-install workflow

- **Source:** [`.github/workflows/h2-h1-offline-ci.yml` lines 17–47](https://github.com/physicsvigilante/sim_heat/blob/f2bb5369425a250cef78b74baaf486925f8fa6bd/.github/workflows/h2-h1-offline-ci.yml#L17-L47); [`tools/h1_native_batch.py` lines 50–104, 181–237](https://github.com/physicsvigilante/sim_heat/blob/f2bb5369425a250cef78b74baaf486925f8fa6bd/tools/h1_native_batch.py#L50-L104).
- **Observed by source and CI-log inspection:** The integration workflow installs version-pinned Python dependencies using `pip install` before the test suite. It has no `omc`, `buildModel`, batch-runner call or native build/launch step; its GitHub token permission is read-only and action references are SHA-pinned. The *separate*, non-CI batch runner checks an input-plan hash, per-file hashes, branch/event/attempt and versions, uses bounded case counts/timeouts, invokes subprocesses without a shell and strips GitHub credential environment variables for native processes.
- **Trust boundary:** Installing dependencies is a normal **network-capable installation step** (not a malicious side effect or demonstrated vulnerability). `GITHUB_ACTIONS`/branch environment checks and user-supplied hashes are **not** strong execution authentication or isolation of hostile Modelica files; the runner is safe only for specifically trusted, approved plans and inputs on controlled hosts. Its native process has no general-purpose network sandbox.
- **Advice:** Describe this CI as **offline physical/numerical checking, with dependency installation** rather than an air-gapped test. Do not present the runner as an arbitrary-untrusted-Modelica service. Stronger wheel hash locks or OS/network isolation are future hardening if that trust model changes. **Not a blocker for this scoped integration**; no untrusted native execution in current CI was identified.
